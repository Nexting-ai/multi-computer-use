## What it shows

- **Execution was not the bottleneck; writing the actions was.** One cursor spent about as long acting as thinking: roughly 1.5 s per decision of 8 actions. Twelve cursors meant the model wrote up to 96 actions per decision. Each such decision then took about 14 s of thinking on 701, so the hands that should have worked in parallel waited on the planning. In this editor actions are cheap (well under a second). The model's cost per action stays the same however many hands carry it out.
- **Big unchecked batches made mistakes.** On 702, both arms that act in large batches without looking in between (multi and one-wide) stopped at 0.64. Each had 14 arrows attached the wrong way. The single cursor, which looks after every 8 actions, was complete on all three diagrams.
- **Concurrency had a real cost.** On 701, twelve cursors at once produced overlapping shapes and lost bindings. The agent then deleted 52 elements and redrew.
- **Twelve agents think in parallel, so they start fastest** (50% in 53–79 s, against 113–154 s for the others). But without coordination none finished: 6–16 wrong arrows each, at 7× the tokens of one agent.
- **Where many cursors do help:** when each action takes the application a while (the canvas runs: 0.8 s per click, 3.2× faster). For a local, responsive editor, one agent with one cursor remained the best.
